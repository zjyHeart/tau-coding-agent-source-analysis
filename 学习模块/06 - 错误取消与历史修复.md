# 06 - 错误取消与历史修复

> [!summary] 本章解决什么
> 成功路径之外，Agent 还要回答：工具不存在、执行异常、provider 出错、用户取消时，history 是否保持可继续的形状？本章用确定性测试逐个看失败分支。

**官方概念参考**：[The agent loop](https://twotimespi.dev/concepts/#the-agent-loop)。这页说明当前 Tau 的概念；本章具体代码行为仍以 `c66fb879` 源码和测试为准。

**本章定向阅读（同 commit 官方文档）**：[源文件](https://github.com/huggingface/tau/blob/c66fb879c1058f7b3d8514fb7f92c919d3c3e3b3/website/content/internals/agent-loop.md) 的「Event-first design」。读完先回答：①错误作为哪种消息或事件出现？ ②取消后怎样补齐悬空工具调用？

## 前置与产物

- 前置：[[05 - Harness 与事件订阅]]。
- 源码：`src/tau_agent/loop.py` 的 `_execute_tool_call()`、`_run_tool()`；`src/tau_agent/harness.py` 的取消与修复；`src/tau_agent/tool_history.py`。
- 产物：五行故障矩阵，每行含触发方式、AgentEvent、最终消息、下一次 provider 看见什么。

## 步骤 1：未知工具

将 `toy_agent.py` 的 `ToolCall.name` 改成未注册的 `missing`，工具注册保持 `read_demo`。预期 `ToolResultMessage.is_error=True`、文字为 `Tool missing not found`，随后 FakeProvider 仍可给出下一轮回答。对照 `tests/test_agent_loop.py::test_agent_loop_records_unknown_tool_as_canonical_error_result`，指出错误结果是谁构造的。

## 步骤 2：工具代码抛异常

恢复工具名，把练习中的 `read_demo` 改为 `raise RuntimeError("boom")`。预期错误结果文字为 `boom`，`is_error=True`；它与“工具未注册”走的分支不同。读 `_run_tool()` 的异常捕获，并记录 `asyncio.CancelledError` 为什么单独向外传播。练习结束后恢复 toy 原版；不要改固定源码中的测试。

## 步骤 3：provider 出错与上限

读 `tests/test_agent_loop.py::test_agent_loop_converts_provider_error_to_assistant_error_message` 和 `test_agent_loop_stops_with_assistant_error_after_max_turns`。前者保留一个 `stop_reason="error"` 的 assistant；后者在超过上限时生成终止错误。再看 `test_agent_loop_excludes_empty_failed_assistant_from_next_provider_call`，分清持久历史与下次传给 provider 的上下文。

## 步骤 4：取消与 dangling tool call

先读 `tests/test_agent_harness.py::test_cancelled_run_notifies_listeners_of_interrupted_tool_repair`，再读 `test_entry_path_repair_is_pushed_to_listeners`。取消后缺少结果的 tool call 会补一个错误 `ToolResultMessage`；补齐还必须通过事件推给订阅者，否则持久化监听者可能漏写。`tool_history.py` 处理给 provider 回放时的缺口/顺序；Harness 的修复还要照顾持久化事件。

## 步骤 5：集中验证

~~~bash
rtk uv run pytest tests/test_agent_loop.py tests/test_agent_harness.py tests/test_tool_history.py -q
~~~

重点查 `tests/test_tool_history.py::test_missing_result_gets_synthetic_interruption` 与 `test_orphan_result_is_dropped_without_inventing_a_call`。不要只记“系统能恢复”，要说明修复发生在进入下一次模型调用前还是结束清理时，以及结果给谁看。

## 完成检查

能独立解释未知工具、工具异常、provider 错误和用户取消各由谁处理；能画出“缺失工具结果 → synthetic result → listener → 可恢复 history”。若把 `CancelledError` 也描述为普通工具结果，回看步骤 2 与 4。

## 同步复刻任务（自己的学习版）

扩展自己的 loop：未知工具和工具异常都产生带错误标记的 tool result；provider 错误产生 assistant 错误；缺结果的 call 在恢复前补 synthetic result。至少写四个独立测试。**内核验收要包含取消修复**：可只复刻“取消后发现 dangling call → 补 synthetic result → 通知 listener”这个确定性场景，无需复刻 Tau 的全部异步 teardown；明确它不是普通工具异常。
