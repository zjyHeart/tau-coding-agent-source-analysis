# 14 - 最小复刻与最终验收

> [!summary] 本章解决什么
> 把前面逐章写的学习版组件集成，并按**内核入门**与**完整工程**两层验收。每项都对应前面明确要求的实现任务；做完 00–07 不需要通过持久化与 UI 验收。学习版不是生产级 coding agent。

**官方概念参考**：[Core concepts](https://twotimespi.dev/concepts/)（复盘全部概念）。这页说明当前 Tau 的概念；本章具体代码行为仍以 `c66fb879` 源码和测试为准。

**本章定向阅读（同 commit 官方文档）**：[源文件](https://github.com/huggingface/tau/blob/c66fb879c1058f7b3d8514fb7f92c919d3c3e3b3/website/content/concepts.md) 的「The agent loop / Sessions / Two interfaces」。读完先回答：①内核入门验收要证明什么？ ②完整工程验收新增哪几层？

## 前置与产物

- 前置：内核入门验收需完成 [[00 - 环境与学习边界]] 至 [[07 - Coding 工具与安全边界]]；完整工程验收再完成 08–13。
- 工作目录：本笔记目录下的 `tau-playground/mini_tau/`。固定源码保持原状。
- 内核产物：消息模型、fake provider、工具注册、loop、事件、Harness 队列、错误/取消修复与对应测试。
- 工程产物：在内核上增加配置、prompt、JSONL Session、最简 renderer 和扩展 hook；每个新增能力单独验证。
- 自己的测试位置：`tau-playground/tests/`；从 `tau-playground/` 运行 `rtk uv run --project ../tau-source python -m pytest tests -q`。

## 第一层：内核入门验收（对应 01–07）

### 1. 消息与 fake provider（模块 01–02）

检查 user、assistant、tool result、tool call 的必要字段与 ID；测试四条消息的顺序与配对。再测普通回答只有一次 fake provider 调用、两条 history 消息；text delta 只增加事件，不增加消息。参考 [[01 - Agent 闭环与消息协议]]、[[02 - FakeProvider 与单轮回答]]。

### 2. 工具与 loop（模块 03–04）

收到 tool call 后查表执行、追加结果、再问 fake provider。集成测试断言 **2 次 provider 调用、4 条 history 消息、1 次工具执行、ID 配对正确**。另测没有 call 时停止、达到 `max_turns` 时停止，不接 PackyAPI。

### 3. Harness 与排队输入（模块 05）

重跑事件顺序、listener 订阅/取消订阅、重叠启动被拒绝、**follow-up 排队后被消费**四类测试。这里的 follow-up 是模块 05 的必做实现；若缺失，回模块 05 补，不在验收章临时发明新需求。

### 4. 失败、取消与安全边界（模块 06–07）

分别断言未知工具、工具抛异常、provider 错误、最大轮数、取消后 synthetic tool result；还要确认修复事件能被 listener 看到。只在自己创建的 UTF-8 文件上验证学习版 read 的路径、offset/limit 和缺失文件；不要求复刻 Tau 的 Bash、write、edit。

**入门通过标准：**自己的测试覆盖以上四组，能不看源码讲清“用户消息 → 模型提出 call → 程序执行 → 结果回填 → 模型再回答”。本层不要求 JSONL、压缩、TUI 或真实模型。

## 第二层：完整工程验收（对应 08–13）

1. **配置与 prompt（模块 08–09）：**配置结构区分 base URL、模型 ID、API 形状、凭证环境变量名；无密钥测试验证字段与错误输入。prompt 测试验证资源加载许可、拼接顺序与去重。真实 PackyAPI 是选做，不把连接成功当作单元测试通过。
2. **持久化与恢复（模块 10–11）：**UTF-8 JSONL 追加后可线性恢复；两个分支末端产生不同投影；缺 parent 报错；取消修复可以落盘；摘要只改变活动上下文，原始行仍保留。符合 v0.4.5 的末端 entry 规则，不写旧式 `LeafEntry`。
3. **展示与扩展（模块 12–13）：**同一事件流产生“只输出最终文本”和“包含工具过程”的两种 renderer；只读扩展工具可注册，before-hook 拒绝可见，重复注册遵守自己的规则。无需实现 Textual 或 Tau 完整扩展兼容接口。

**工程通过标准：**上述每一项都有对应模块的实现和独立测试；能画出配置 → runtime/provider → Harness → Session → renderer 的路径，并列出学习版缺少的 OAuth、真实协议适配、TUI、安全隔离和动态 provider 生命周期。

## 如何运行与提交学习证据

从 `tau-playground/` 执行 `rtk uv run --project ../tau-source python -m pytest tests -q`，保存测试输出与一页“我的实现 / Tau v0.4.5 对应函数 / 尚未实现”的对照表。不要把 Tau 原仓库的测试通过数当成自己 `mini_tau` 的通过数。若进一步修改 Tau 自身，另建独立工作树，以有针对性的测试验证，不在固定学习快照中混入改动。
